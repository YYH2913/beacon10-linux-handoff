# Build inputs, output files and flashing boundary

All commands below build **local files**, not a live router. This repository
ships no universal flash image and keeps ordinary live installation disabled.
Store backups, keys, extracted firmware and generated artifacts outside the
repository, or in the ignored `.private/` and `build/` directories.

## 1. Supply your own inputs

- A complete, supported eMMC user-area backup, named `mmcblk0.img` inside a backup
  directory, exactly 1,954,545,664 bytes long.
- Modules extracted from the same stock root: `qca-nss-dp.ko`, `qca-ssdk.ko`, and
  the `xtables-legacy-multi` executable with its ELF dependencies for recovery
  firewall cleanup.
- Matching stock-kernel headers/build tree. Exact vendor GPL source is preferable.
- Static ARM64 BusyBox and Dropbearmulti, plus **your own SSH public key**.
- A target Image, DTB and SquashFS rootfs with a separately implemented and
  validated receiver.

A matching product name is not evidence of firmware compatibility. SHA constants
bind the audited stock build. Supporting another build requires a fresh ABI
audit, not just replacing hashes or disabling checks.

## 2. Generate the stock profile from your backup

Run from the repository root. Set all uppercase variables to your own absolute
paths; output directories must not already exist.

```sh
python3 -B tools/beacon10/stock-kernel-profile.py "$BACKUP_DIR" \
  --out "$PROFILE_OUT"
```

Outputs include `stock-Image`, `stock.config`, `System.map`, `profile.json` and
`stock-profile.h`. They are derived from your private stock backup: **do not
commit or redistribute them with this repository**. The tool accepts an ordinary
offline image, not a block device.

The supported profile requires Linux 5.4.164, module loading, disabled
MODVERSIONS/module signatures/kexec, and the known uncompressed kallsyms and
instruction layout. Earlier integration used upstream Linux 5.4.164 prepared
with the stock configuration, not exact vendor source. Comparing vermagic,
struct module and exported symbols reduces risk; it does not prove every
private kernel ABI.

If preparing a separate Linux 5.4.164 tree, operate on **your own build copy**:

```sh
cp "$PROFILE_OUT/stock.config" "$KERNEL_HEADERS/.config"
make -C "$KERNEL_HEADERS" ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- olddefconfig modules_prepare
```

The builder requires an exact `UTS_RELEASE` of `5.4.164` and compares the stock
module's vermagic, struct module size/alignment, init/exit offsets and all strong
imports. A mismatch stops the build. Do not patch vermagic or force-load a module.

## 3. Build the stock-side module

First build the read-only probe, which contains no shutdown or jump path:

```sh
python3 -B tools/beacon10/build-stock-probe.py \
  --profile "$PROFILE_OUT" --headers "$KERNEL_HEADERS" \
  --stock-module "$STOCK_ROOT/lib/modules/5.4.164/qca-ssdk.ko" \
  --out "$PROBE_OUT"
```

Build the real **sender** module:

```sh
python3 -B tools/beacon10/build-stock-probe.py --handoff \
  --profile "$PROFILE_OUT" --headers "$KERNEL_HEADERS" \
  --stock-module "$STOCK_ROOT/lib/modules/5.4.164/qca-ssdk.ko" \
  --stock-dp-module "$STOCK_ROOT/lib/modules/5.4.164/qca-nss-dp.ko" \
  --out "$MODULE_OUT"
```

The outputs are `beacon10-handoff.ko` and `probe-validation.json`. The builder
adds the audited stock-power-v1 sender operations. **Do not run Kbuild directly
in the `handoff/` template directory instead**: the template alone is not the
complete production power-handoff module. Historical RAM experiment modes are
not exposed by the public CLI.

Generated `stock-dp.h` and `stock-rpm-profile.h` contain fingerprints extracted
from your stock programs and belong in a private build directory. This repository
publishes the generators, not those generated bytes. They are sender inputs,
not the omitted target-kernel receiver.

## 4. Build the minimal bootstrap

BusyBox needs mount flags, gunzip/tar, ip/mdev/insmod/udhcpd and the recovery
applets listed by the builder. `check-busybox.py` uses qemu-user to validate
flags and archive handling without mounting a filesystem. Dropbear must be
static and support public-key authentication; there is no default SSH password.

```sh
python3 -B tools/beacon10/build-handoff-bootstrap.py \
  --busybox "$BUSYBOX" --module-build "$MODULE_OUT" \
  --stock-root "$STOCK_ROOT" --dropbear "$DROPBEAR_MULTI" \
  --authorized-key "$SSH_PUBLIC_KEY" --out "$BOOTSTRAP_OUT"
```

Outputs:

- `rootfs/`: generated directory tree.
- **`bootstrap.squashfs`:** minimal root plus handoff components, limited to
  6 MiB even though each slot is 8 MiB.
- `manifest.json`: hashes and build checks, **not hardware acceptance**.

It includes `/sbin/init`, `/bin/b10-loader`,
`/lib/modules/5.4.164/beacon10-handoff.ko`, BusyBox, SSH recovery and your
stock Ethernet dependencies. Normal handoff does not load recovery networking
modules or start the stock Wi-Fi stack.

**The `.ko` is not flashed separately. `bootstrap.squashfs` is the filesystem
content for P26/P27.** It contains your public key and stock dependencies; do not
treat it as a redistributable generic release image.

## 5. Build the target payload and installation bundle

The previous steps do not make an ordinary QSDK kernel a compatible receiver.
The following packaging steps apply **after** receiver implementation:

```sh
python3 -B tools/beacon10/build-handoff-payload.py \
  --kernel "$TARGET_IMAGE" --dtb "$TARGET_DTB" --out "$PAYLOAD_OUT"
make host-tools
build/host/b10-loader --verify "$PAYLOAD_OUT/boot.bin"
python3 -B tools/beacon10/build-install-bundle.py \
  --bootstrap "$BOOTSTRAP_OUT/bootstrap.squashfs" \
  --boot "$PAYLOAD_OUT/boot.bin" --rootfs "$TARGET_ROOTFS" \
  --verifier "$PWD/build/host/b10-loader" --out "$INSTALL_BUNDLE"
```

- **`boot.bin`:** 4096-byte B10LINUX-v1 header, raw ARM64 Image and 4 KiB-aligned
  DTB. It is not a FIT or OEM-signed package. It belongs in P29, not in HLOS.
- **Target rootfs SquashFS:** the P30 root, with the `stock-linux-v2` storage marker.
- **B10INST2 bundle:** three components with their transaction hashes. It is not
  a complete GPT disk image and must not be copied directly over the disk.

`build-ram-installer.py` can construct a maintenance archive, but its public
entry rejects `--install`. `b10-install --image ... --apply` accepts regular
files only. `--check-device` is an explicit read-only device entry; repository
checks never call it. Removing the gate does not make this a safe universal
flashing tool.

## 6. File-to-partition mapping

For an already correct `stock-linux-v2` layout:

- P24/P25: retain the stock signed HLOS; **do not write project files here**.
- P26/P27: two copies of the same `bootstrap.squashfs`.
- P29: `boot.bin`.
- P30: target rootfs SquashFS.
- P36: target writable overlay, initialized only by matching receiver policy;
  it is not another SquashFS destination.
- P37: device-bound snapshots and boot journal, created by a controlled
  transaction, never copied from another unit.

This is an address contract, not a flashing procedure. First installation also
requires identity relocation, ordered GPT publication, state records and a
fully detached RAM environment. Replacing P26/P27 alone is insufficient.
Upgrading an already migrated device must not repeat migration or erase P36.
See [partitions and migration](partitions-and-migration.md).

## 7. Validation and local-only tests

The export was checked locally using synthetic GPT/CID/DTB/payload data against
the real C parsers, journal, module arguments, CPU/watchdog failure handling,
layout, permissions, sender build ordering and publication boundary. **Test
sources stay local and are not committed.** Host tools and static ARM64 tools
were compiled; the trampoline was assembled and checked for external
relocations, not executed through a real MMU/cache transition.

Public `make host-tools arm64-tools check` and build CI do not depend on local
test scripts. `check` only verifies generated layout constants. Private
regular-file migration fault runs need owner-supplied backups and matching
bundles; their test drivers are not published either.

No live migration, block-device write, module load or CPU jump was performed
for this export. Offline success is not permission or evidence to flash a device.
